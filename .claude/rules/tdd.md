# TDD Rule

> **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸지 않는다.

## 우선순위

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선**한다.
- 이 파일은 **기본값(fallback)** 이다. 프로젝트 규칙이 없거나 침묵하는 부분에만 적용한다.

## 적용 기준

**반드시 TDD 적용:**
- 비즈니스 로직
- API (핸들러, 요청/응답 처리)
- 유틸 / 순수 함수
- 버그 수정 (**먼저 버그를 재현하는 실패 테스트를 작성**)

**TDD 불필요:**
- 타입 정의
- 설정 파일
- 순수 UI (로직 없는 마크업/스타일)
- SQL

경계가 모호하면 적용 대상으로 취급한다.

## RED - GREEN - REFACTOR

### 1. RED: 실패하는 테스트 작성
- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 섞지 않는다.
- **반드시 실행해서 실패를 확인한다.** 실행하지 않은 테스트는 테스트가 아니다.
- 실패 이유가 **"기능 미구현"** 이어야 한다. 오타, import 오류, 문법 오류로 인한 실패는 RED가 아니다. 고친 뒤 다시 실행한다.

### 2. GREEN: 최소한의 코드
- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI.** 테스트가 요구하지 않는 기능, 옵션, 추상화를 추가하지 않는다.
- **신규 테스트와 기존 테스트 모두 통과**하는지 실행해서 확인한다.

### 3. REFACTOR: 정리
- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **green을 유지**한다. 변경 후마다 테스트를 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작은 새 RED에서 시작한다.

### 4. 반복
- 다음 동작에 대해 **RED로 돌아간다.** 모든 요구 동작이 끝날 때까지 반복한다.

## 삭제 강제 규칙

- **테스트 전에 프로덕션 코드를 먼저 작성했다면 삭제하고 RED부터 재시작한다.**
- **"참고용"으로 남기는 것도 금지.** 주석 처리, 별도 파일 보관, 복사해 두기 모두 포함한다. 보고 베끼면 테스트 주도가 아니다.

## 변명 차단표

| 변명 | 반론 |
|------|------|
| 너무 단순해서 테스트 불필요 | 단순한 코드는 테스트도 30초면 끝난다. 단순한 코드가 가장 자주 조용히 깨진다. |
| 나중에 테스트 추가하겠다 | 나중에 쓴 테스트는 구현을 따라 쓰게 되어 버그를 못 잡는다. 바로 통과하는 테스트는 아무것도 증명하지 못한다. |
| 시간이 없다 | 디버깅과 회귀 수정이 더 오래 걸린다. TDD가 더 빠른 경로다. |
| 삭제하면 낭비다 | 매몰 비용 오류다. 검증 안 된 코드를 유지하는 것이 진짜 낭비다. 다시 쓰는 건 빠르다. |
| 프로토타입이다 | 프로토타입은 프로덕션이 된다. 버릴 코드라면 테스트도 필요 없지만, 남길 코드라면 지금 테스트한다. |
