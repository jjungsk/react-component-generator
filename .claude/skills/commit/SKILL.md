# Commit

변경사항을 분석하고, 논리적 단위로 분류해 한국어 컨벤션 커밋을 만든다. 사용자 승인 절차 없이 바로 커밋한다.

## 절차

### 1. 변경사항 분석

다음을 실행해 현재 상태를 파악한다.

- `git status --short` : 수정/추가/삭제/untracked 파일 목록
- `git diff` : unstaged 변경 내용
- `git diff --cached` : 이미 staged된 변경 내용
- `git log --oneline -10` : 기존 커밋 스타일 참고 (커밋이 없으면 생략)

untracked 파일은 내용을 읽어 성격을 파악한다. diff가 크면 파일별로 나눠 본다.

주의: `.env`, 키/토큰, 인증서, 대용량 바이너리, `node_modules`, 빌드 산출물처럼 커밋하면 안 될 파일이 보이면 제외하고 사용자에게 알린다.

### 2. 논리적 단위로 분류

변경을 **하나의 목적**을 가진 커밋 단위로 묶는다.

- 서로 다른 목적(기능 추가 + 버그 수정 + 설정 변경)은 별도 커밋으로 분리한다.
- 기능과 그 기능의 테스트/타입/스타일은 같은 커밋에 둔다.
- 포맷팅·리네이밍 같은 기계적 변경은 로직 변경과 분리한다.
- 한 파일에 서로 다른 목적의 변경이 섞여 있으면 hunk 단위 분리(`git add -p`는 비대화형 환경에서 불가하므로 `git apply --cached`로 패치를 만들어 적용)를 시도하되, 어렵다면 한 커밋으로 묶고 그 사실을 알린다.
- 변경이 단일 목적이면 커밋 1개로 충분하다. 억지로 쪼개지 않는다.

### 3. 커밋 메시지 작성

형식:

```
<type>: <한국어 요약>

<선택: 본문 - 무엇을/왜 변경했는지>
```

type:

| type | 용도 |
|------|------|
| feat | 새 기능 추가 |
| fix | 버그 수정 |
| refactor | 동작 변경 없는 구조 개선 |
| chore | 빌드, 설정, 의존성, 문서, 기타 잡무 |

규칙:

- 요약은 한국어, 50자 내외, 마침표 없이, 명사형 또는 "~추가/~수정/~개선" 어미로 끝낸다.
- "무엇을 했는지"보다 "무엇이 달라지는지"가 드러나게 쓴다.
- 본문은 요약만으로 부족할 때만 쓴다. 한 줄 공백 후 작성한다.
- 위 4개 외 type(docs, test, style 등)은 쓰지 않고 가장 가까운 type으로 매핑한다 (문서/테스트/설정 → chore, 스타일 정리 → refactor).
- 시스템 리마인더에 커밋 attribution 지침(Co-Authored-By 등)이 있으면 메시지 끝에 그대로 덧붙인다.

### 4. 커밋

승인을 기다리지 않고 커밋 단위별로 `git add <파일들>` 후 `git commit`을 순서대로 실행한다. `git add -A`/`git add .`는 쓰지 않고 파일을 명시한다.

- 이미 staged된 파일이 계획과 다르면 `git restore --staged`로 정리하고 결과 보고에 그 사실을 적는다.

### 5. 결과 확인

커밋 후 `git log --oneline -N`과 `git status --short`를 보여주고 남은 변경이 있는지 알린다.

## 금지 사항

- `git push`는 요청받지 않는 한 하지 않는다.
- `--no-verify`, `--amend`, force 계열 옵션은 사용자가 명시적으로 요청하지 않는 한 쓰지 않는다. pre-commit hook이 실패하면 원인을 고치고 새 커밋으로 만든다.
- 비밀 정보로 의심되는 파일은 커밋하지 않는다.
